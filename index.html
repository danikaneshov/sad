02 · Корень темы

Какое облачное хранилище выбрать?

Облако — это не «один большой диск». Разные паттерны чтения и записи требуют специализированных движков хранения.

01 · OBJECT STORAGE

Объектное хранилище

AWS S3 · Google Cloud Storage · Cloudflare R2

Хранит неизменяемые файлы: фото, видео, PDF, бэкапы. Масштабируется практически бесконечно и отдельно от БД.

E-commerce пример:

Фото товара (2.4 МБ) → ссылка в CDN

02 · OLTP DATABASE

Операционная БД (OLTP)

PostgreSQL · MySQL · CockroachDB

Таблицы и связи, строгие ACID-транзакции, B-Tree индексы, тысячи частых точечных чтений и записей в секунду.

E-commerce пример:

Заказ ORD-1042, списание баланса

03 · OLAP WAREHOUSE

Аналитическое хранилище

BigQuery · ClickHouse · Snowflake

Колоночное хранение, высокое сжатие и массово-параллельные агрегации по миллионам и миллиардам строк.

E-commerce пример:

Отчёт продаж за год по регионам

Интерактивное сравнение: OLTP vs OLAP
03 · Управляемые сервисы

DBaaS и модель разделения ответственности

Database as a Service (Supabase, AWS RDS, Neon, Google Cloud SQL) снимает рутину администрирования серверов, но не снимает ответственность за данные.

Слои ответственности

Разработчик Облачный провайдер

✓ Почему выбирают DBaaS

  • Запуск production-кластера PostgreSQL за 2 минуты.
  • Автоматические патчи безопасности и point-in-time бэкапы.
  • Встроенный мониторинг, метрики и авто-failover.

! Компромиссы и риски

  • Стоимость на больших объёмах: при росте трафика и IOPS чек выше, чем на своём железе.
  • Vendor Lock-in: привязка к проприетарным фичам провайдера (если не использовать стандартный SQL).
  • Плохой индекс «уронит» даже самый дорогой DBaaS.

КРИТИЧЕСКАЯ БЕЗОПАСНОСТЬ

Почему нельзя класть service_role ключ во фронтенд?

Любой код в браузере (JS-бандл, вкладка Network в DevTools) полностью открыт пользователю. Ключ service_role / secret обладает правами суперпользователя и полностью обходит политики RLS.

✓ В браузере (Frontend)

Только публичный anon ключ + строгие RLS-правила в PostgreSQL.

✕ Только на сервере (Backend)

service_role в переменных окружения (.env), скрытых от клиента.

PostgreSQL · Row Level Security (RLS) schema.sql 
-- 1. Включаем защиту на уровне строк
ALTER TABLE public.demo_orders
  ENABLE ROW LEVEL SECURITY;

-- 2. Пользователь видит ТОЛЬКО свои заказы
CREATE POLICY "Users see own orders"
  ON public.demo_orders
  FOR SELECT
  USING ( auth.uid() = user_id );

Даже если злоумышленник изменит REST-запрос в браузере, движок PostgreSQL автоматически добавит условие WHERE auth.uid() = user_id.

            06 · Рост нагрузки
            
Масштабирование: Vertical vs Horizontal

          


          
          

            

              

                
Вертикальное (Scale Up)

                ↑ CPU / RAM / NVMe
              

              

                Усиливаем один сервер. Плюс: не нужно менять код приложения. Минус: есть физический потолок железа и короткий простой при апгрейде.
              

            

            

              

                
Горизонтальное (Scale Out)

                → Read Replicas · Sharding
              

              

                Добавляем узлы: Read Replicas забирают чтение, PgBouncer управляет коннектами, а Шардирование делит запись между серверами.

              RTO
              

                Recovery Time Objective — максимальное допустимое время простоя. Автоматический Failover снижает RTO до 15–30 секунд.
              

            

            

              RPO
              

                Recovery Point Objective — сколько данных допустимо потерять (во времени). Синхронная репликация даёт RPO = 0.
              

            

          

        

      

    


    
    

      

        

          

            08 · Аналитический контур
            
Data Lake, Data Warehouse и Lakehouse

          


          
          

            
1. Источники (БД, клики, логи)

            →
            
2. Data Lake (сырые данные)

            →
            
3. ETL / ELT (очистка, dbt)

            →
            
4. Data Warehouse (витрины, BI)

          


          
          

            

              
Data Lake

              
Schema-on-Read · S3 / Parquet / JSON

              

                Дёшево хранит петабайты сырых логов, событий и медиа. Идеально для Data Science и обучения ML-моделей.
              

            


            

              
Data Warehouse

              
Schema-on-Write · BigQuery / ClickHouse

              

                Очищенные, строго структурированные витрины. Мгновенные SQL-агрегации для BI-дашбордов и финотчётов.
              

            


            

              
Data Lakehouse

              
Apache Iceberg · Delta Lake

              

                Современный гибрид: ACID-транзакции и скорость витрин прямо поверх дешёвого объектного хранилища S3.

            09 · Индустриальные кейсы
            
Как это работает в реальных проектах

            

              Крупные системы почти никогда не используют одну базу — они комбинируют сервисы под каждую задачу (Polyglot Persistence).
            

          


          

            
            

              

                
                

                
                  E-COMMERCE · ПИКИ
                
              

              

                

                  
Маркетплейс в «Чёрную пятницу»

                  

                    При 10-кратном росте трафика каталог и корзина обслуживаются из кэша, заказы пишутся в транзакционную БД, а дашборд продаж обновляется в реальном времени.
                  

                

                

                  PostgreSQL (заказы)
                  Redis (корзина)
                  S3 + CDN (фото)
                  ClickHouse (BI)
                

              

            


            
            

              

                
                

                
                  ФИНТЕХ · RPO = 0
                
              

              

                

                  
Банкинг и платёжный процессинг

                  

                    Потеря даже одного перевода недопустима. Используется синхронная Multi-AZ репликация, строгая изоляция транзакций и неизменяемый аудит-лог.
                  

                

                

                  Multi-AZ Sync DB
                  Strict ACID
                  WORM Audit S3
                

              

            


            
            

              

                
                

                
                  IoT · BIG DATA

            11 · Итоги и проверка
            
4 золотых правила и блиц-тест

          


          
          

            

              
ПРАВИЛО 01

              
Храните файлы в S3, заказы в OLTP-БД, а отчёты стройте в OLAP Warehouse.

            

            

              
ПРАВИЛО 02

              
Никогда не кладите service_role ключ во фронтенд — используйте RLS.

            

            

              
ПРАВИЛО 03

              
Реплика спасает от сбоя железа, но от случайного DELETE спасёт только PITR-бэкап.

            

            

              
ПРАВИЛО 04

              
Перед шардированием включите индексы, Connection Pooler и Read Replicas.
